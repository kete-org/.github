# Security Policy

Security matters to us and to the businesses that rely on Kete products. Thank you for helping keep KeteOS, Kete Code and our users safe.

## Reporting a vulnerability

**Please do not report security issues through public GitHub issues, pull requests or discussions.**

Instead, report them privately in either of these ways:

- **Email:** security@your-website.com
- **GitHub:** use **"Report a vulnerability"** under the affected repository's **Security** tab (private vulnerability reporting)

Please include as much of the following as you can:

- The product, repository and version or commit affected
- The type of issue (e.g. authentication bypass, injection, data exposure)
- Steps to reproduce, or a proof of concept
- The potential impact, and how an attacker might exploit it
- Any suggested fix, if you have one

## What to expect

| Stage | Our target |
|---|---|
| Acknowledge your report | Within **3 business days** |
| Initial assessment and severity rating | Within **10 business days** |
| Status updates | At least every **2 weeks** until resolved |

When a fix is ready, we will coordinate disclosure timing with you. We're happy to credit you publicly unless you'd prefer to stay anonymous.

## Supported versions

We provide security fixes for the latest release of each product. Please make sure you can reproduce the issue on the current version before you report it.

## Guidelines for researchers

We won't take legal action against good-faith security research that:

- Avoids privacy violations, data destruction, and disruption to our services or users
- Only accesses or changes data in accounts you own, or with the account holder's explicit permission
- Gives us reasonable time to fix the issue before any public disclosure

The following are **out of scope**:

- Denial-of-service and load testing
- Social engineering or phishing of Kete staff or users
- Physical attacks
- Vulnerabilities in third-party services we don't control

Thank you for helping us keep Kete secure.
